# Как запустить сервер управления (termit-mn)

[English](../using-mn.md) · [Русский](using-mn.md)

Сервер управления — та самая машина, которая держит прокси-сеть в порядке: он хранит список участников,
проверяет каждый узел снаружи и отдаёт каждому владельцу подписку. Ваш трафик через него не идёт.

Нужно: Debian 13 (2 vCPU, 2 ГБ RAM, 10 ГБ диска), root, DNS-имя, указывающее на машину, и свободные
порты 80 и 443. Одного сервера хватает на группу до нескольких десятков узлов, а если он упадёт, установленные соединения продолжат работать. Второй сервер может держать копию реестра и отвечать узлам, чей ведущий сервер недоступен,  — см. [Второй сервер](#второй-сервер); это репликация, а не кластер: у каждого узла по-прежнему один ведущий сервер.

Если проще выбрать из списка, чем вспоминать флаги, запустите `termit-mn` без аргументов на сервере — это
[интерактивное меню](menu.md).

## Установка

Скачайте установщик и запустите его: он находит самый свежий релиз, сверяет его контрольную сумму,
ставит бинарник и юнит, ставит пробник, создаёт конфигурацию, запускает службу и печатает состояние.
`wget` есть не всегда: в минимальном и netinst-образе Debian нет ни его, ни `curl`, поэтому сначала
поставьте что-то одно (`apt-get update && apt-get install -y wget`); `curl -fsSLO <тот же URL>` тоже
подойдёт:

```bash
apt-get update && apt-get install -y wget   # только если в образе нет ни curl, ни wget
wget -q https://github.com/shogun-kub/termit/releases/latest/download/mn.sh
sh mn.sh --domain mn.example.com --email you@example.com --admin-token-out /etc/termit/mn/admin.token
```

`--version vX.Y.Z` поставит указанный релиз вместо самого свежего; `--base-url` направит скрипт на
зеркало, `file://`-URL или локальный каталог (там `--version` обязателен: зеркало не может ответить,
какой релиз самый свежий). Повторный запуск скрипта — это обновление, и флагов оно не требует: домен
берётся из установленной конфигурации, свежий релиз определяется заново, служба перезапускается.
`--mode` передаётся в `init`:

| Режим | Что происходит при вступлении узла |
|---|---|
| `invite` | кода приглашения достаточно |
| `invite+approval` (по умолчанию) | узел ждёт как `pending`, пока вы не выполните `termit-mn uv approve` |
| `open` | приглашение не нужно — разумно только в приватной сети |

Поменять режим позже: `termit-mn invite policy --mode <режим>` — правит одно значение в `config.yaml`,
сохраняет ваши комментарии и отказывается включать `open` без `--force`. Режим читается при старте,
поэтому команда заканчивает напоминанием: работающий сервер держит старое правило до
`systemctl restart termit-mn`. `termit-mn invite policy` без `--mode` печатает действующее правило.

Обновление самого сервера — `termit-mn update`: без флагов спросит у GitHub самый свежий опубликованный
релиз и скажет, отстаёт ли эта сборка. `--apply` скачает его, сверит дайджест с `SHA256SUMS` релиза,
оставит прошлый бинарник как `termit-mn.prev`, перезапустит службу и вернёт старый бинарник, если
перезапуск не удался. Команды сознательно нет в `status`: сервер отвечает на вопросы о прокси-сети,
а проверка, ходившая в GitHub при каждом `status`, была бы его единственной сетевой зависимостью,
кроме своих узлов. `--release-base` указывает на зеркало.

`termit-mn init` создаёт конфигурацию, базу, мастер-ключ и первый админ-токен и печатает секреты **один
раз** (`--admin-token-out` пишет токен в файл вместо печати):

```
domain:       mn.example.com
listen:       :443
api prefix:   /6rfjdqfn5nno
masking site: portal (what a prober gets for every path the API does not claim)
config:       /etc/termit/mn/config.yaml
database:     /var/lib/termit/mn/termit.db (schema 9)
master key:   /etc/termit/mn/master.key (generated now)

admin token (shown once, store it now):
  <token>

first invite code (shown once, 1 use(s)):
  ABCD-EFGH-IJKL
```

Обратите внимание на две вещи. **Префикс API** — это путь, по которому живёт API узлов:
`init` выбирает случайный, поэтому сканер, пробующий `/api/v1`, на вашем сервере не находит ничего, а
каждый узел получает полный URL — `https://mn.example.com/6rfjdqfn5nno`, — а не голый домен. Это не
секрет, и [справочник по API](../../MN-API.md) описывает, что за ним стоит.
`--api-prefix /api/v1` оставляет старый, обнаруживаемый путь, если он нужен.

**Сайт-приманка** — это то, что видит посетитель: обычная на вид страница на `/`, собственная 404
для всего остального и ни слова про Termit. Хост, который на любой путь отвечает `404 page not found`,
сам по себе отпечаток. `--decoy-template product` выбирает другой архетип (на узлах те же два), позже
это делает `decoy.template` в конфигурации. Страница генерируется при старте и живёт в памяти — на
диске нет ничего, что можно было бы отредактировать.

Две вещи нужно сохранить, и сохранить вместе: **админ-токен** (без него не работает ни одна команда
`mn`) и **мастер-ключ** (`/etc/termit/mn/master.key`). Без мастер-ключа база не сможет вывести ни
одной пары учётных данных — это не пароль, который можно сбросить, это соль всего реестра. Храните их с
резервной копией базы, но не рядом с ней.

Положите токен в окружение, чтобы он не попал в историю шелла:

```bash
export TERMIT_MN_ADMIN_TOKEN='<token>'
```

Или храните его в файле — это то, что нужно таймеру, cron-задаче или Ansible: у них нет шелла, из
которого можно экспортировать переменную. CLI читает файл только когда его об этом просят, и
отказывается от файла, за который не может поручиться:

```bash
# записать один раз, и так, чтобы никто другой не прочитал
install -m 0600 /dev/null /etc/termit/mn/admin.token
printf '%s\n' '<token>' > /etc/termit/mn/admin.token

termit-mn status --token-file /etc/termit/mn/admin.token
export TERMIT_MN_ADMIN_TOKEN_FILE=/etc/termit/mn/admin.token   # или указать один раз в шелле
```

Файл должен быть с правами `0600` и принадлежать тому пользователю, который запускает команду; всё
остальное отклоняется: ошибка называет `chmod`, который это исправит. Файл, читаемый группой или
всеми, — это утёкшие учётные данные, которые выглядят как аккуратная настройка.

`termit-mn init --admin-token-out FILE` записывает токен сразу в файл с правами `0600`, а не печатает
его — чтобы у подготовленного сервера единственная копия не жила в чьей-то прокрутке терминала:

```bash
termit-mn init --domain mn.example.com --email you@example.com \
  --admin-token-out /etc/termit/mn/admin.token
```

Если запись не удалась, `init` всё равно напечатает токен и завершится с ошибкой: к этому моменту токен
уже есть в базе, а токен, которого никто не видел, оставил бы сервер без администратора.

Если токен утёк — обновите его. Команда заменяет токен, которым аутентифицировалась (свой,
а не чужой), и один раз отдаёт новый:

```bash
termit-mn admin rotate --token-out /etc/termit/mn/admin.token
```

Каждый скрипт, таймер и playbook, в котором ещё лежит старый токен, перестаёт работать в этот же
момент. Ради этого обновление и делают, и это же стоит проверить перед запуском. Для обновления нужен
текущий токен: если потерян именно он, порядок восстановления — в
[руководстве по восстановлению](../../RUNBOOK.ru.md#админ-токен-потерян).

## Первый запуск

Скрипт ставит юнит и запускает службу. Вручную это те же шаги:

```bash
install -m 0644 termit-mn.service /etc/systemd/system/
systemctl daemon-reload
systemctl enable --now termit-mn
journalctl -u termit-mn -n 30 --no-pager
```

В том же релизе — юниты защиты сервера (`termit-mn-firewall*`, `termit-mn-guard`,
`termit-mn-blocklist*`). Их ставят, только если вы решили защищать сервер, а межсетевой экран без них
отказывается работать: остальное — на странице [Защита узла](hardening.md).

Первый запуск **выпускает сертификат до того, как начать отдавать TLS**, и отказывается стартовать,
если выпустить не удалось: API управления, тихо откатившийся на HTTP, хуже, чем неподнявшийся.
Ожидайте минуту-две, затем:

```
level=INFO msg="issued a certificate" domain=mn.example.com not_after=…
level=INFO msg="serving TLS" domain=mn.example.com listen=:443 not_after=…
level=INFO msg="admin socket ready" path=/run/termit/mn/admin.sock
```

Проверка:

```bash
curl -sS https://mn.example.com/6rfjdqfn5nno/healthz   # {"status":"ok", …}
termit-mn status                                       # печатает и префикс API
```

`termit-mn status` — экран, который открывают первым каждый раз:

```
server:   mn.example.com
listen:   :443
api:      /6rfjdqfn5nno
decoy:    portal
version:  termit-mn vX.Y.Z (commit …, built …, api 1, profile v1)
uptime:   3h12m (started 2026-11-10 11:18)
database: /var/lib/termit/mn/termit.db (412.0 KiB, schema 9)
prober:   ready (/usr/local/lib/termit/xray)
queue:    0 due, next 2026-11-11 12:34 UTC
cert:     2027-02-08T12:06:44Z (in 89 days)
mesh:     mn_6f3c0a5e1b2d4c8f (master key: yes, epoch 2)
  peer mn2      https://mn2.example.com/6rfjdqfn5nno — up to date (41 entries)
nodes:    3 (3 active)
check:    every 24h, times below are UTC

DOMAIN             STATE   FAILED  LAST CHECK         NEXT CHECK         LAST SEEN
node1.example.com  active  0       2026-11-10 13:29   2026-11-11 12:34   2026-11-10 13:31
```

Две строки выдают прокси-сеть, которая только выглядит здоровой: `prober: unavailable` значит, что ни одна
проверка не может дать вердикт (все узлы остаются как были, ничего не блокируется), а растущее
`queue: N due` — что планировщик не успевает. Ни то, ни другое — не отказ узла.

Сервер продлевает свой сертификат сам: выпускает при старте, перепроверяет каждые шесть часов и
подменяет файл без перезапуска. Строка `cert:` показывает, что он реально отдаёт.

## Приглашение узлов

```bash
termit-mn invite create --note "узел Ани" --uses 1
termit-mn invite create --uses 5 --expires-hours 48      # партия с дедлайном
termit-mn invite list
termit-mn invite revoke ABCD-EFGH-IJKL
```

Код приглашения — секрет с ограниченным числом использований; передавайте его по каналу, которому
доверяете, и отзывайте, если он утёк. Каждое использование расходует одно место.

`invite create` печатает то, что нужно переслать: команду, запускающую визард, и два ответа, которые спросят
у человека на другом конце помимо его собственного домена:

```
send this to them (the wizard asks for their own domain; these are the other two answers):

  sh uv.sh --wizard
  server: https://mn.example.com/6rfjdqfn5nno
  invite: ABCD-EFGH-IJKL

for: узел Ани
```

## Наблюдение и управление узлами

| Задача | Команда |
|---|---|
| список узлов | `termit-mn uv list` |
| посмотреть один узел | `termit-mn uv show node1.example.com` — состояние, история, последняя проверка и самопроверка |
| одобрить ожидающий узел | `termit-mn uv approve node1.example.com` |
| отклонить ожидающий узел | `termit-mn uv reject node1.example.com` |
| заблокировать узел самому | `termit-mn uv block node1.example.com --reason "жалоба"` |
| снять свою блокировку | `termit-mn uv unblock node1.example.com` |
| убрать узел из прокси-сети | `termit-mn uv rm node1.example.com` |
| стереть запись | `termit-mn uv forget node1.example.com` (только после удаления) |
| прочитать ключ агента | `termit-mn uv agentkey node1.example.com` |
| заменить ключ агента | `termit-mn uv reissue node1.example.com` |
| проверить сейчас | `termit-mn check now node1.example.com` или `termit-mn check now --all` |
| поправить расписание | `termit-mn policy show`, `termit-mn policy set check_interval 12h` |
| удлинить или укоротить грейс | `termit-mn policy set block_after_failed_cycles 4` — сколько провалов подряд блокируют узел (по умолчанию 2, то есть одна грейс-проверка) |
| обновить токен подписки | `termit-mn sub rotate node1.example.com --domain mn.example.com` |

Что означают состояния:

| Состояние | Значение | Чем снимается |
|---|---|---|
| `pending` | вступил, но ещё не одобрен (`invite+approval`) | `termit-mn uv approve` |
| `active` | проверен и работает | — |
| `unavailable` | проверка выполнилась и честно провалилась (сертификат, приманка, туннель) | успешными проверками |
| `blocked` | настроенное число провалов подряд (`policy.block_after_failed_cycles`, по умолчанию 2) или решение оператора | `termit-mn uv unblock` или запрос самого узла `termit-uv unblock` |
| `removed` | вне прокси-сети; учётные данные перестают работать | повторным вступлением (новая запись) |

Состояние меняется только по вердикту. Проверка, которая не смогла выполниться — пробник не отвечает,
DNS на сервере сломан, таймаут — даёт `unknown` и ничего не меняет. Поэтому узел может выглядеть
«зависшим» в `termit-mn uv show` и при этом быть в порядке.

`block` и `unblock` — ваше слово против слова пробника: успешная проверка не снимает вашу блокировку,
и именно это не даёт «мигающей» проверке мигать всей прокси-сетью.

## Подписки

У каждого узла один токен. Адреса:

| URL | Содержимое |
|---|---|
| `https://mn.example.com/sub/<token>` | base64 из ссылок, по строке на ссылку, — тот самый «URL подписки», который нужен клиенту; узел с включённым QUIC-транспортом добавляет рядом с `vless://` свою `hy2://` |
| `https://mn.example.com/sub/<token>/json` | те же пиры как профиль sing-box: селектор, `direct` для приватных диапазонов и выход `hysteria2`, если узел его отдаёт |

Оба стабильны при неизменном составе пиров и несут `ETag`, поэтому кэширующий клиент обходится одним
`304`. Свой URL узел показывает в `termit-uv status`. Обновление токена мгновенно отменяет старый URL и не
затрагивает локальные устройства узла — они с машины никуда не уходят.

Узел в состоянии `pending` или `removed` списка не получает: его URL отвечает `404`, как и неизвестный
токен. У `blocked` URL остаётся, но соседи уже выкинули его учётные данные, так что через прокси-сеть
ничего не работает до разблокировки.

## Резервные копии и восстановление

```bash
termit-mn backup                                        # <data_dir>/backups/termit-<timestamp>.tar.gz
termit-mn backup --out /root/mn-backup.tar.gz
```

В архиве база и мастер-ключ. Держите его зашифрованным и храните копию вне сервера: у кого оба, у того
все парные учётные данные прокси-сети.

```bash
termit-mn restore --from /root/mn-backup.tar.gz --force  # сервер сначала остановить
```

Восстановление — офлайн-операция: остановить `termit-mn`, восстановить, запустить. Восстановленная база
полезна только с тем же мастер-ключом — если база есть, а ключа нет, узлам придётся вступать заново.

## Второй сервер

Второй `termit-mn` может держать копию реестра, чтобы узел, чей ведущий сервер недоступен, всё равно
получал ответ: последнее состояние, которое опубликовал ведущий сервер, с пометкой `read_only` («только чтение»), а
отчёт узла ждёт в очереди до возвращения ведущего. Это не кластер и не балансировщик: у каждого узла ровно
один ведущий сервер, и только он пишет его строку.

1. **Дайте обоим серверам один мастер-ключ**, один раз и вручную: файл ключа первого скопируйте
   второму, режим `0600`. Хост, у которого есть ключ, может вывести учётные данные любого узла, поэтому
   ключ кладут только на машину, которой позволено принять узлы. `serve` читает также `TERMIT_MN_MASTER`,
   поэтому резервному серверу можно передать ключ, ни разу не записав его на диск, а `termit-mn status`
   печатает, откуда этот процесс его взял.
2. **Укажите второй сервер на обеих сторонах** в `config.yaml`: `mesh.peers` с именем, базовым адресом
   (вместе с префиксом API пира) и необязательным `leaf_sha256`, плюс `pull_every` и `lag_max`. Затем
   перезапустите оба. Каждый раз в `pull_every` читает журнал другого; первый опрос берёт снимок всего
   реестра.
3. **Читайте блок `mesh:` в `termit-mn status`**: id этого сервера, эпоха и по каждому пиру — ответил
   ли он и насколько отстал.

Передача узла между ними — явная команда: `termit-mn home handoff --uv <id|домен> --to <пир>` выдаёт узлу
новый агентский ключ, поднимает поколение на единицу и печатает две команды, которые выполняют на узле.
Ведущий сервер, который больше не вернётся, — `termit-mn home adopt --from <пир>`: команда отказывается,
пока старый ведущий сервер отвечает; узлы, вступившие после последней синхронизации этого сервера, здесь
неизвестны, и им нужно вступить заново. `termit-mn epoch rotate` заново выводит все парные учётные данные
и отказывается, если не ответил хотя бы один настроенный пир.

Полный порядок действий — ключ, имя, отказы — в [`OPERATIONS.md`](../OPERATIONS.md) §3.4.

## Мониторинг

`/metrics` доступен только на loopback, в формате Prometheus, и никогда не называет узел:

```
termit_mn_up 1
termit_mn_nodes{state="active"} 3
termit_mn_check_queue_due 0
termit_mn_prober_up 1
termit_mn_checks_total{result="ok"} 42
termit_mn_certificate_expiry_timestamp_seconds 1801439850
```

На что ставить алерты: пропал `up`, `certificate_expiry_timestamp_seconds` меньше недели,
растёт `check_queue_due`, `prober_up 0`, растёт `checks_total{result="failed"}`. Детали по узлам
остаются в `termit-mn uv show` и журналах — у этого адреса намеренно нет инвентаря.

Сервер ведёт журнал systemd — структурированный, с идентификаторами узлов и без учётных данных:

```bash
journalctl -u termit-mn -f
```

| Команда | Что делает |
|---|---|
| `termit-mn init` | создать конфигурацию, базу, мастер-ключ, админ-токен и первое приглашение; `--admin-token-out FILE` пишет токен в файл вместо печати; `--locale ru\|en` задаёт язык меню |
| `termit-mn serve` | запустить сервер (`--http` только для разработки, никогда на публичном адресе) |
| `termit-mn invite create\|list\|revoke\|policy` | управление кодами приглашений и правилом вступления для нового узла |
| `termit-mn uv list\|show\|approve\|reject\|block\|unblock\|rm\|forget\|reissue\|agentkey` | управление узлами |
| `termit-mn check now <узел>\|--all` | выполнить проверки немедленно |
| `termit-mn home handoff --uv <узел> --to <пир>` | передать один узел другому серверу: новый агентский ключ, следующее поколение и две команды для узла |
| `termit-mn home adopt --from <пир> [--uv <узел>]` | принять узлы сервера, который больше не вернётся; отказывается, пока тот отвечает |
| `termit-mn epoch rotate` | заново вывести все парные учётные данные прокси-сети; отказывается, если не ответил хотя бы один настроенный пир |
| `termit-mn uv forget --force <узел>` | стереть копию строки, которую ведёт другой сервер; в журнал ничего не пишется |
| `termit-mn policy show\|set` | посмотреть или изменить пороги планировщика |
| `termit-mn sub rotate <узел>` | выпустить новый токен подписки |
| `termit-mn admin rotate` | заменить админ-токен, которым команда аутентифицировалась; `--token-out FILE` пишет его в файл |
| `termit-mn status` | сервер, узлы, расписание |
| `termit-mn backup`, `termit-mn restore` | снимок и восстановление |
| `termit-mn update` | поставить самый свежий опубликованный релиз: `--check` (по умолчанию) только сообщает, `--apply` заменяет бинарник и перезапускает службу |
| `termit-mn firewall` | собственная таблица сервера: `status`, `on`, `off`, `confirm`, `refresh`, `restore` |
| `termit-mn bans`, `termit-mn guard` | движок банов на сервере |
| `termit-mn version` | версия сборки и протокола |

Админ-команды общаются с работающим сервером через unix-сокет (`/run/termit/mn/admin.sock`) и
аутентифицируются по `TERMIT_MN_ADMIN_TOKEN`, `TERMIT_MN_ADMIN_TOKEN_FILE`, `--token` или `--token-file`.
Они никогда не открывают базу в обход сервера.

Межсетевой экран, баны и страж — та же необязательная механика, что и на узлах, только со своим именем
таблицы и своими портами: об этом — страница [Защита узла](hardening.md).

## Правила, которые стоит соблюдать

- **Никогда не правьте базу руками.** Это реестр; интерфейс — админ-команды.
- **Делайте резервную копию мастер-ключа с базой и шифруйте копию.** Без ключа ничего не восстановить.
- **Один сервер на одну базу.** Два экземпляра на одной базе её испортят, и второй всё равно не сможет выпустить сертификат на то же имя. Второй *сервер* — это реплика со своей базой, см. [Второй сервер](#второй-сервер).
- **Держите строку `prober` в `termit-mn status` зелёной.** Пробник мёртв — прокси-сеть цела, но слепа.
- **Берегите админ-токен как мастер-ключ.** Он создаётся в `termit-mn init` и хранится хешем; `termit-mn
  admin rotate` заменяет его, и старый перестаёт работать сразу. Держите его в файле с правами `0600`, а
  не в истории шелла, и не включайте в копии, которыми делитесь.
