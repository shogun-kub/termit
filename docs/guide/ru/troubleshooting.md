# Если что-то пошло не так

[English](../troubleshooting.md) · [Русский](troubleshooting.md)

Обычно ничего не ломается: агент просыпается раз в сутки, сервер проверяет каждый узел по своему
расписанию, сертификаты продлеваются сами. Когда это перестаёт быть правдой, смотреть нужно в таком
порядке.

## Три команды для начала

```bash
uv doctor                  # на узле: здоровье машины и узла, по строке на проверку
uv status                  # идентичность, сертификат, пиры, синхронизация, WARP
mn status                  # на сервере: prober, очередь, сертификат, таблица узлов
```

`uv doctor` печатает подсказку рядом с каждой неудачной проверкой, а `mn uv show <узел>` на сервере
показывает последнюю проверку и последнюю самопроверку вместе — так видно, «сломалась машина» или
«сломан путь до неё». Дальше: `journalctl -u termit-uv-agent` на узле и `journalctl -u termit-mn` на
сервере.

## Прочитать до паники

- **`unknown` — это не отказ.** Проверка, которая не смогла выполниться — prober упал, DNS на сервере
  сломан, таймаут — ничего не меняет. Узлы сохраняют состояние, пиры продолжают работать. Сеть, где
  все проверки `unknown`, — слепая, а не мёртвая: чинить нужно наблюдателя.
- **`pending` — это нормально.** В режиме `invite+approval` узел ждёт оператора. Он не сломан, и
  переустанавливать его не нужно.
- **`direct` — это не авария.** При включённом WARP и fail-open (по умолчанию) мёртвый туннель значит,
  что проксируемый трафик выходит с вашего адреса. Всё работает, адрес просто ваш.
- **Повторный запуск безопасен.** Каждый шаг установки идемпотентен: `uv init` ещё раз доводит
  состояние до нужного и не перегенерирует ни идентичность, ни учётные данные, ни сертификаты.

## Установка сервера

| Симптом | Вероятная причина | Что делать |
|---|---|---|
| `mn init` отказывает: `domain is required` | нет `--domain` | передайте имя, которое резолвится на эту машину |
| `mn serve` выходит: `cert: listen on :80` | порт 80 занят | освободите его (`ss -lntp`) или задайте `acme.challenge_listen` и пробросьте порт |
| `mn serve` выходит с ошибкой ACME | DNS ещё не указывает сюда, или порт 80 закрыт | проверьте `dig +short mn.example.com` и доступность порта снаружи |
| `mn serve` выходит: `cannot read the master key` | `/etc/termit/mn/master.key` отсутствует или недоступен | восстановите из резервной копии — без него реестр бесполезен |
| `mn status` говорит `cannot reach the server at …` | сервис не запущен или сокет переехал | `systemctl status termit-mn`, затем `admin_socket` в конфигурации |
| команды `mn` требуют `an admin token is required` | не задан `TERMIT_MN_ADMIN_TOKEN` | экспортируйте его или передайте `--token` |
| команды `mn` говорят `the admin token is not valid` | не тот токен, или база восстановлена без таблицы `admin` | используйте токен, который напечатал `mn init` |

## Вступление узла

| Симптом | Вероятная причина | Что делать |
|---|---|---|
| `uv init` остановился на `ports` | на 80/443 уже что-то слушает | остановите это и повторите `uv init` |
| `uv init` остановился на `dns` | запись пока не резолвится сюда | поправьте DNS; самой установке он не нужен, вступлению — да |
| `uv init` остановился на `certificate` | порт 80 недоступен из интернета или DNS неверен | проверьте и то и другое снаружи; `uv init --only certificate` повторит только этот шаг |
| `uv enroll` → `dns_mismatch` | домен резолвится в другое место, или запрос шёл через прокси | поправьте A/AAAA и повторите: сервер сравнивает запись с адресом, с которого пришёл запрос |
| `uv enroll` → `invalid_invite` | код с опечаткой, отозван, истёк или израсходован | `mn invite list` на сервере, создайте новый |
| `uv enroll` → `domain_taken` | запись с таким доменом уже есть | `mn uv show <домен>`; удалите старую запись или возьмите другое имя |
| `uv enroll` → `rate_limited` | десять неудачных попыток за пятнадцать минут с одного адреса | подождите и повторите |
| узел остаётся `pending` | режим `invite+approval` | `mn uv approve <узел>` на сервере |
| `uv enroll` → ошибка TLS | сертификат сервера ещё не доверен узлу | проверьте `uv doctor` → `acme` и что часы на узле верны |

## Ежедневная работа

| Симптом | Вероятная причина | Что делать |
|---|---|---|
| узел `unavailable`, хотя ручная проверка проходит | prober не может до него добраться | `mn uv show` покажет класс; проверьте `prober.xray_binary` и собственный выход сервера |
| `mn status` пишет `prober: unavailable — every check reports unknown` | не удалось создать рабочий процесс prober | прочитайте причину в строке, поправьте `prober.xray_binary`, перезапустите `termit-mn`; узлы остаются как были |
| в `mn status` растёт `queue: N due` | планировщик не успевает | `journalctl -u termit-mn`; зависший prober видно здесь раньше, чем меняется состояние узла |
| узел `blocked` сразу после обновления | сертификат заменили, а сервер ещё помнил старый | следующая синхронизация принесёт новый лист; если остался `blocked` — `uv unblock` |
| список пиров устарел | суточная синхронизация ещё не прошла (она раз в сутки, так задумано) | `uv sync` |
| `uv sync --check` выходит с кодом 4 | набор клиентов в ядре расходится с серверным | `uv sync` |
| в `uv status` старый `last sync` | агент не работает | `systemctl status termit-uv-agent`, `journalctl -u termit-uv-agent` |
| узел пропал после перезагрузки | юниты не включены | `uv init` включит и запустит их снова |

## Сертификаты

| Симптом | Вероятная причина | Что делать |
|---|---|---|
| `uv doctor` → `certificate` warn/fail | продление опаздывает или сломано | `uv renew-cert`; журнал `termit-uv-renew.service` скажет почему |
| сертификат истёк | продление долго не могло достучаться до CA | `uv renew-cert --force` после проверки DNS и порта 80 |
| сертификат сервера истёк | шестичасовое продление всё время падало | журнал `termit-mn` называет ошибку ACME; старый сертификат остаётся в работе до выпуска нового, поэтому чинить нужно путь до CA, а не перезапуск |
| `uv renew-cert` → challenge failed | порт 80 недоступен или DNS уехал | поправьте и повторите |

## Выход в интернет и WARP

| Симптом | Вероятная причина | Что делать |
|---|---|---|
| `uv status` показывает `warp: … direct` | WARP упал, fail-open делает своё дело | `uv warp status`, затем `journalctl -u warp-cli`; трафик всё равно работает |
| `uv warp status` показывает `not-installed` | узел ставили с `--no-warp` или пакет удалили | `uv init` или `uv warp mode all` установит и зарегистрирует |
| `uv warp status` показывает `unavailable` | машина не умеет WARP: нет `/dev/net/tun` или нет пакета под архитектуру | чинить нечего — причина напечатана; узел работает и выходит напрямую |
| `uv warp mode` → `start-limit-hit` | слишком много перезапусков за пять минут | `systemctl reset-failed termit-xray termit-uv-agent`, затем повторить |

## Подписки и клиенты

| Симптом | Вероятная причина | Что делать |
|---|---|---|
| подписка отдаёт `404` | токен повернули или он с опечаткой | `uv status` покажет актуальный URL; `mn sub rotate` выпустит новый |
| клиент показывает старых пиров | он не обновился | обновите вручную; URL несёт `ETag`, поэтому кэширующий клиент стоит одного `304` |
| клиент подключается, но трафика нет | учётные данные пира повернули, или узел `blocked` | `mn uv show <узел>`; заблокированный узел выпадает из всех подписок |
| URL подписки утёк | это учётные данные | `mn sub rotate <узел> --domain <mn>`; старый URL сразу перестанет работать |

## Как просить помощи

Соберите это и вставьте в issue — отвечает на девять вопросов из десяти и не содержит учётных данных:

```bash
uv version; uv status; uv doctor
journalctl -u termit-uv-agent -n 100 --no-pager
# на сервере
mn version; mn status
mn uv show <этот узел>
journalctl -u termit-mn -n 100 --no-pager
```

Никогда не присылайте `state.json`, `/etc/termit/uv/config.yaml`, мастер-ключ и админ-токен: в них
учётные данные. Если у вас просят конфигурацию, пришлите вывод
`sed -E 's/(key|token|uuid|secret)[^:]*: .*/\1: <redacted>/I' /etc/termit/uv/config.yaml`.
