# Runbook

[English](RUNBOOK.md) · [Русский](RUNBOOK.ru.md)

Что делать, когда что-то не так: все команды запускайте от `root`, а ссылка на
[`OPERATIONS.md`](OPERATIONS.md) стоит там, где хочется понять, почему это работает именно так. Начните
с §1 и найдите строку, которая совпадает с тем, что вы видите.

## 1. Первые пять минут

| Что видно | Вероятная причина | Что делать |
|---|---|---|
| `termit-uv init` останавливается на `preflight` с `ports` failed | на 80/443 уже кто-то слушает | `ss -H -ltnp`, остановите его, запустите `termit-uv init` заново |
| на preflight `dns` warn | запись ещё не резолвится с этой машины | направьте A/AAAA-запись на машину; установке это не нужно, вступлению — да |
| `termit-uv enroll` → `dns_mismatch` | домен резолвится в другой адрес или запрос пришёл через прокси | поправьте DNS; проверка сравнивает запись с адресом TCP-соединения |
| `termit-uv enroll` → `rate_limited` | десять неудачных попыток за пятнадцать минут с одного адреса | подождите и повторите; окно считается по адресу |
| `termit-uv enroll` → `domain_taken` | запись с таким доменом уже есть | `termit-mn uv show <домен>`; сначала уберите или перенесите её |
| узел застрял в `pending` | режим `invite+approval` | `termit-mn uv approve <узел>` |
| узел `unavailable`, хотя ручная проверка проходит | пробник до него не дотягивается | `termit-mn uv show` покажет класс; проверьте `prober.xray_binary` и собственный выход сервера |
| `termit-mn status` пишет `prober: unavailable — every check reports unknown` | не удалось создать рабочий процесс пробника | прочитайте причину в той же строке, поправьте `prober.xray_binary`, перезапустите `termit-mn`; узлы остаются как были, ничего не блокируется |
| в `termit-mn status` растёт `queue: N due` | планировщик не успевает | `journalctl -u termit-mn` — ошибки планировщика; зависший пробник здесь виден раньше, чем меняется состояние узла |
| узел стал `blocked` сразу после обновления | сертификат заменили, а сервер всё ещё держал старый лист | следующая синхронизация принесёт новый лист; `termit-uv sync`, затем `termit-uv unblock`, если узел остался заблокированным |
| `termit-uv doctor` → `services` failed | какой-то юнит не работает | `systemctl status <юнит>`; `termit-uv init` запустит их снова |
| `termit-uv doctor` → `certificate` warn/fail | продление опоздало или сломано | `termit-uv renew-cert`; журнал `termit-uv-renew.service` скажет почему |
| `termit-uv status` показывает `warp: … direct` | WARP упал, и fail-open делает своё дело | `termit-uv warp status` назовёт причину; трафик при этом работает |
| `termit-uv warp status` показывает `not-installed` | личности WARP нет: ставили с `--no-warp` или состояние удалили | `termit-uv init` (или `termit-uv warp mode all`) зарегистрирует и поставит туннель; команда в этом состоянии возвращает 0 |
| `termit-uv warp mode` → `start-limit-hit` | слишком много перезапусков за пять минут | `systemctl reset-failed termit-xray termit-uv-agent` |
| `termit-uv sync --check` выходит с кодом 4 | набор клиентов в ядре отличается от серверного | `termit-uv sync` |
| команды `mn`: `cannot reach the server at …` | `termit-mn` не запущен или сокет переехал | `systemctl status termit-mn`; проверьте `admin_socket` в конфигурации |
| `termit-mn serve` отказывается стартовать: `cert: listen on :80` | `:80` занят (например, nginx на той же машине) | освободите порт или задайте в `acme.challenge_listen` свободный порт и пробросьте его |
| `termit-mn serve` отказывается: `cannot read the master key` | файла ключа нет или он не читается | восстановите из копии; без него реестр бесполезен |
| SQLite `database is locked` | база на медленной или сетевой файловой системе, либо её открыл второй процесс | держите базу на локальном диске; админ-команды идут через сервер, а не напрямую |
| подписка отдаёт `404` | токен обновили или он с опечаткой | `termit-uv status` покажет текущий адрес; `termit-mn sub rotate` выдаст новый |
| `termit-uv upgrade` → `the server has not reported its version yet` | узел не синхронизировался с тех пор, как эта сборка научилась запоминать версию сервера | `termit-uv sync`, затем `termit-uv upgrade`; либо назовите релиз: `--to vX.Y.Z` |
| `termit-uv upgrade` → `did not converge the node` | новый бинарник не смог свести конфигурацию этой машины | предыдущий бинарник уже возвращён на место, больше ничего не изменилось; исправьте то, что напечатал шаг, и запустите снова |
| `termit-mn update --apply` → `the previous binary is back in place; restart the server to run it` | новая сборка не пережила перезапуск | `systemctl restart termit-mn`, прочитайте журнал, затем `termit-mn status` |

Когда ничего явно не сломано, порядок такой: `termit-uv doctor` на узле, `termit-mn uv show` на
сервере, потом оба журнала. Проверка, которая говорит `unknown`, — это отказ наблюдателя, а не узла;
так и напишите в отчёте, вместо того чтобы «чинить» узел.

## 2. Узел в `blocked`, а сам он в порядке

```bash
termit-uv unblock                    # заново проверяет DNS и туннель со своего адреса, потом синхронизируется
```

Если не получилось, команда печатает причину, которую назвал сервер: `dns_mismatch` — запись указывает не
на эту машину; `check_failed` — туннель не ответил через сайт-приманку. Исправьте это и запустите снова.
Сами состояния описаны в [`OPERATIONS.md`](OPERATIONS.md) §9.1.

## 3. Сервер управления пропал

Восстанавливайте из резервной копии (§10 ниже). Без копии прокси-сеть заново не собрать: каждый узел
придётся заново ввести в неё. Парные учётные данные выводятся из мастер-ключа, а мастер-ключ из узла не
восстановить.

**Если есть реплика, узлы работают, пока вы это читаете.** Второй `termit-mn` с тем же
мастер-ключом и настроенным `mesh.peers` отвечает каждому узлу последним состоянием, которое у него есть,
с пометкой `read_only`, и откладывает отчёт для ведущего сервера. Путей назад два, и порядок такой:

1. **Машина вернулась.** Спасать нечего: реплика уже отдала ей очередь отчётов, а `mn.url` у узлов не
   менялся. Сверьте блок `mesh:` в `termit-mn status` на обоих.
2. **Машина не вернётся.** Переведите имя на реплику и выполните на ней
   `termit-mn home adopt --from <пир>`: реплика заберёт строки и сохранит агентские ключи, поэтому на
   узлы идти не нужно. Узлы, вступившие после последней синхронизации реплики, там неизвестны — им
   нужно вступить заново. Узел, ушедший на третий сервер, возвращают командой
   `home handoff --uv <узел> --to <пир>`, когда тот отвечает.

Полный порядок действий — ключ, имя, возврат узлов — в `OPERATIONS.md` §3.4.

## 4. Утёк админ-токен

Обновите его: команда заменяет те учётные данные, которыми вы прошли проверку, и старый токен
перестаёт работать в тот момент, когда выпущен новый:

```bash
termit-mn admin rotate --token-out /etc/termit/mn/admin.token
```

Для обновления нужен текущий токен: без него это был бы захват, а не обновление.
Команда затрагивает только строку администратора, который прошёл проверку. До запуска перечислите, где
ещё лежит старый токен: любой таймер, cron-задача или плейбук с ним упадёт на следующем запуске с
`the admin token is not valid`. `--token-out` пишет новый токен с правами `0600`; без него токен
печатается один раз и больше нигде не хранится, так что потерянный вывод означает потерянное обновление.

### Админ-токен потерян

Для обновления нужен текущий токен, поэтому это единственный случай, когда восстановить его можно
только офлайн: сервер намеренно хранит только дайджест. Снимите резервную копию базы, удалите строку `admin` и
дайте `init` выпустить новые учётные данные:

```bash
apt-get install -y sqlite3                        # в минимальном Debian его нет
sqlite3 /var/lib/termit/mn/termit.db 'delete from admin;'
systemctl restart termit-mn
termit-mn init --config /etc/termit/mn/config.yaml --admin-token-out /etc/termit/mn/admin.token
```

`init` на уже установленном сервере сохраняет все остальные решения — домен, listen, мастер-ключ,
узлы — и только добавляет недостающего администратора. Считайте это инцидентом: у того, кто держал
старый токен, был реестр, и дайджест в базе больше с ним не совпадает.

## 5. Узел пересобран на той же машине

```bash
termit-uv init --domain node1.example.net --relocate --agent-key-file /root/agent-key
termit-uv migrate --relocate
```

Вторая команда сообщает серверу о новом self-UUID и сертификате; без неё сервер продолжает проверять
старую личность, и узел остаётся в `blocked` или `unavailable`.

### Узел переехал на новую машину

```bash
termit-uv init --domain node5.example.net --relocate --agent-key-file /root/agent-key
termit-uv migrate --relocate --domain node5.example.net
```

Старая запись переиспользуется, поэтому у пиров остаются те же парные учётные данные, а в их списках
на следующей синхронизации меняются только домен и путь. Новый домен должен резолвиться в новую машину,
а машина — отдавать профиль, который заявляет; иначе сервер откажет в переезде и оставит запись как
была.

## 6. Часы уплыли

Первыми ломаются ACME и TLS. `timedatectl status`; поправьте `systemd-timesyncd` или `chrony`, затем
`termit-uv renew-cert --force`, если заказ остался незавершённым.

### Узел сообщает о расхождении

```bash
termit-uv sync --check        # код выхода 4 и diff
termit-uv sync                # сойтись сейчас
```

Расхождение означает, что набор клиентов в ядре отличается от серверного — так выглядит ручная правка
или пропущенная синхронизация. Следующий цикл всё равно бы это исправил; `termit-uv sync` делает это
сейчас.

## 7. Узел отвечает, но часть соединений уходит в таймаут

Клиент или пробник подключается только часть времени, в журналах узла чисто, а `ss -s` показывает на узле
записи `syn-recv`. Termit не сообщает об ошибке, потому что Termit тут не виноват: пакеты теряются между
двумя сетями. Проходите пункты по порядку — каждый снимает целый класс причин.

1. **Контроль с той же машины.** Десять соединений к постороннему известному адресу (резолвер, крупный
   сайт). Если и они не проходят, проблема в канале узла, и узел тут ни при чём.
2. **Обход портов.** По двенадцать попыток на `:443`, `:80`, `:22` и на закрытый порт. Если каждый порт
   теряет одну и ту же долю, потери привязаны к адресу назначения, а не к порту — значит, фильтра по
   портам нет.
3. **Темп.** Измерьте после двух минут простоя, затем сразу после пачки из 40 соединений. Та же потеря в
   покое — это не ограничение скорости и не шейпер, реагирующий на вас.
4. **Счётчики узла**, дважды с интервалом 60 с, пока с другой стороны идёт поток попыток:

   ```bash
   nstat -az | grep -E 'TcpExtListenDrops|TcpExtTCPSynRetrans|TcpExtTCPTimeouts'
   ```

   - Растёт `ListenDrops` → очередь прослушивания узла отбросила SYN (backlog или межсетевой экран на самой
     машине).
   - Растёт `TCPSynRetrans`, а `ListenDrops` стоит на нуле → узел получил SYN и повторял SYN-ACK, то есть
     теряется **ответ** на обратном пути.
   - Ничего не растёт → SYN до узла не доходил.

   `termit-uv net` делает это за вас: он снимает те же счётчики в течение `--seconds` (по умолчанию 30) и
   печатает вердикт рядом с сырыми дельтами, готовыми для тикета провайдеру. Он не открывает сокетов,
   никуда не обращается и отвечает `skip`, а не `ok`, когда за время замера трафика не было: тихий узел и
   здоровый выглядят одинаково. Счётчики ядра включают loopback, поэтому переход nginx→Xray тоже
   считается; на этом переходе рукопожатия не теряются, так что названная потеря — осторожная оценка, а
   не завышенная цифра.
5. **Гигиена узла**, которая снимает подозрения с самой машины, а не с пути: `nft list ruleset` (любые
   правила drop или rate), таблица conntrack, если модуль загружен, `net.ipv4.tcp_syncookies` и
   `tcp_max_syn_backlog`. Пустой набор правил, отсутствие conntrack и `syncookies=1` значат, что пакеты
   теряет не ядро.

Так, в ноябре 2026 года измеряли узел, терявший треть всех новых соединений: 12 из 12 с той же машины к
трём посторонним адресам; на узле 8 из 12 на `:443`, 10 из 12 на `:80`, 8 из 12 на `:22`, закрытый порт
ответил `RST` 9 раз из 12; та же потеря после двух минут простоя; под нагрузкой наша сторона повторила
36 SYN на 9 неудачных потоков, а узел ответил `ListenDrops +0`, `TCPSynRetrans +61`, `TCPTimeouts +42`;
в покое узел завершал 35 рукопожатий в минуту и повторял 5 SYN-ACK. Виноват был путь у провайдера в обе
стороны — ядро, межсетевой экран и Termit были ни при чём. Идите с этими цифрами к провайдеру или переносите
узел: никакая настройка Termit не исправит канал с потерями.

## 8. После `firewall on` до машины не достучаться

Прежде всего подождите пять минут: `firewall on` взводит таймер отката **до** применения, и таймер
убирает таблицу, не нуждаясь в SSH. Если доступ ещё есть, `termit-uv firewall confirm` оставит таблицу, а
`termit-uv firewall off` убирает её из любого состояния; правила — в [`OPERATIONS.md`](OPERATIONS.md)
§13.2 и §13.3.

## 9. Обновление

Узлы и сервер — разные бинарники с разными записями: сначала обновляйте сервер, потом узлы. В пределах
`api_version: 1` протокол только дополняется, поэтому смешанный парк продолжает работать.

На MN бинарник может заменить себя сам. `--check` — режим по умолчанию, он ничего не ставит:

```bash
termit-mn update --check      # пройти по releases/latest и сказать, отстаёт ли эта сборка
termit-mn update --apply      # скачать, проверить по SHA256SUMS, подменить, перезапустить
journalctl -u termit-mn -n 20 --no-pager
termit-mn status
```

`--apply` оставляет работавший бинарник как `/usr/bin/termit-mn.prev` и возвращает его, если
`systemctl restart termit-mn` не удался. Неудачное обновление оставляет на месте предыдущий
бинарник. База мигрирует на старте, только вперёд, и предыдущий бинарник более новую схему не прочитает.
`termit-mn update --apply` и `mn.sh` сами снимают резервную копию реестра, печатают её путь
и не идут дальше, если копия не удалась; если вы заменяете бинарник вручную, снимите копию заранее
(§3.5.1) — это единственный путь назад, если новая сборка не сломалась, а просто неверна.
Повторный запуск `mn.sh` по-прежнему нужен, чтобы обновить пробник или юнит: `termit-mn update` их
не трогает.

На узле короткий путь идёт за сервером, а не за лентой релизов:

```bash
termit-uv upgrade --check    # что будет установлено: версия сервера, ничего не скачивается
termit-uv upgrade            # установить её, сохранить termit-uv.prev, свести конфигурацию новым бинарником
termit-uv doctor
```

`termit-uv upgrade` ставит ту версию, которую сервер управления назвал на последней синхронизации,
никогда `latest`. Команда проверяет её, кладёт рядом с работающим бинарником и даёт **ему** запустить
`init`: новый релиз знает, что ему нужно. Неудавшийся свод сам возвращает предыдущий
бинарник. Если команда говорит, что сервер ещё не назвал версию, сначала выполните `termit-uv sync`
(или назовите релиз: `--to v0.7.0`). Установочный скрипт — второй короткий путь: он ставит самый свежий
релиз или тот, что указан в `--version`, и запускает тот же `init`:

```bash
sh uv.sh --no-enroll                     # самый свежий релиз
sh uv.sh --version v0.4.1 --no-enroll    # или ровно этот
```

Вручную это те же два шага:

```bash
install -m 0755 termit-uv.new /usr/bin/termit-uv
termit-uv init                       # сводит каждый шаг; ни одни учётные данные не перевыпускаются
termit-uv doctor
```

`termit-uv init` — это путь обновления для всего, что узел создаёт сам: юнитов, vhost, конфигурации ядра
и закреплённого релиза Xray, когда `xray.version` сдвинулся. Он никогда не переписывает личность,
сертификат, зерно приманки и учётные данные. После этого перезапустите агент, чтобы он подхватил
конфигурацию, которую прочитал на старте:

```bash
systemctl restart termit-uv-agent
```

Перезапуск в разгар серии перезапусков может упереться в лимит запусков systemd. `termit-uv init`,
`termit-uv warp mode` и собственный перезапуск агента сами вызывают `systemctl reset-failed`, поэтому это
уже обработано. Если вы перезапускаете руками и видите `start-limit-hit`, выполните
`systemctl reset-failed termit-xray termit-uv-agent` и запускайте снова.

## 10. Резервная копия и восстановление
### 10.1 Сервер управления (резервная копия и восстановление)

`termit-mn backup` пишет архив с базой, конфигурацией, серверным сертификатом **и мастер-ключом**:

```bash
termit-mn backup                                    # → /var/lib/termit/mn/backups/termit-<ts>.tar.gz
termit-mn backup --out /root/mn-backup.tar.gz
```

В архиве лежит мастер-ключ: из него можно вывести **все парные учётные данные прокси-сети**. Обращайтесь с
ним как с самим ключом: шифруйте при хранении, держите вне сервера и не оставляйте в каталоге, который
читает кто попало. Резервная копия без мастер-ключа восстанавливает реестр, но рабочих учётных
данных из неё не получить.

Восстановление — на новой машине или после аварии:

```bash
install -m 0755 termit-mn /usr/bin/termit-mn
termit-mn restore --from /root/mn-backup.tar.gz        # --force, чтобы заменить существующую базу
install -m 0644 deploy/systemd/termit-mn.service /etc/systemd/system/
systemctl daemon-reload && systemctl enable --now termit-mn
termit-mn status
```

`termit-mn restore` проверяет архив, прежде чем что-то записать. Восстановленный сервер сохраняет учётные
данные всех узлов, поэтому узлы продолжают синхронизироваться без повторного вступления. Если меняется адрес
самого сервера, меняется и `mn.url` у узлов (его пишет `termit-uv init`, либо поправьте `mn.url` и
перезапустите агент).

**Восстановление откатывает админ-токен вместе с базой.** В архиве лежит дайджест, с которым снимали
копию, поэтому токен, выпущенный `admin rotate` после этого, перестаёт работать: это учётные данные в
реестре, а реестр — это и есть копия. Держите токен той резервной копии вместе с самой копией, а после
восстановления обновите его (§4), если того токена у вас больше нет.

Снимайте резервные копии с той частотой, которую обоснуете: раз в день — обычная практика, база маленькая.

### 10.2 Узел

Файл состояния узла — это его личность: self-UUID, путь XHTTP, зерно приманки, агентский ключ и токен подписки.
Потеря означает пересборку узла (сценарий C), а не восстановление.

```bash
tar -C / -czf /root/node1-state.tar.gz \
    etc/termit/uv var/lib/termit/uv            # конфигурация, личность, сертификат, журнал
```

Восстановление этого архива на ту же машину возвращает узел байт в байт, вместе с сертификатом — ради
этого его и стоит держать: восстановление не ждёт заказа в ACME. Не копируйте архив на другую машину и
не продолжайте с ним работать — две машины с одной личностью будут драться за одну запись; для этого
случая есть `termit-uv init --relocate`.

## 11. Удаление
На узле:

```bash
termit-uv uninstall --dry-run     # что будет удалено
termit-uv uninstall               # юниты, vhost, ядро, созданные файлы; конфигурация и состояние остаются
termit-uv uninstall --purge       # ещё конфигурация, состояние, сертификаты и служебный пользователь
```

Что он делает: убирает таблицу межсетевого экрана на хосте, если она применена, отключает туннель WARP,
останавливает и выключает юниты, удаляет все пути, записанные в манифесте установки, возвращает
штатный vhost nginx и перезагружает nginx. Таблица уходит первой и намеренно: таблица с
default-deny и без команды, которая её уберёт, — это машина, которую не починить без консоли. Что он
намеренно оставляет: **пакеты** (nginx может обслуживать другие сайты; `cloudflare-warp` уберите сами,
если хотите) и — без `--purge` — конфигурацию и состояние, чтобы переустановка сохранила ту же личность.

nginx при этом продолжает работать, потому что может обслуживать другие сайты: штатный vhost забирает
`:80` обратно, а `:443` остаётся открытым с уже несуществующим vhost, пока nginx не перезапустят;
`systemctl restart nginx` освобождает порт. `systemctl daemon-reload` тоже стоит выполнить: drop-in с
настройками песочницы с диска удалён, но systemd держит его в кеше и сам об этом предупреждает.

На MN:

```bash
systemctl disable --now termit-mn
rm -f /etc/systemd/system/termit-mn.service /etc/systemd/system/termit-mn-*.service \
      /etc/systemd/system/termit-mn-*.timer
rm -rf /etc/termit/mn /var/lib/termit/mn /usr/local/lib/termit
systemctl daemon-reload
```

`/usr/local/lib/termit` — это пробник, который ставит `mn.sh`; без него переустановленный сервер не сможет
проверить ни одного узла.

Шаблон со звёздочкой накрывает четыре имени юнитов, которые релиз кладёт рядом с серверным —
`termit-mn-firewall`, `-firewall-rollback`, `-guard` и `-blocklist`, шесть файлов вместе с двумя
таймерами ([`OPERATIONS.md`](OPERATIONS.md) §13.6), — их ставит сервер, который хоть раз запускал
`termit-mn firewall on`. Если их оставить, останется загрузочный юнит, который ничего не делает, и
таймер, который продолжает срабатывать.

Команды удаления для сервера нет: у него два каталога с данными, свой каталог для сокета, пробник в
`/usr/local/lib/termit` и свои юниты. Решать за оператора, что реестр пора стереть, автоматическая
команда не должна.

## 12. QUIC-транспорт не поднимается

Ссылка из подписки или со страницы узла не работает, а TLS-профиль на том же узле — работает. Проходите
по порядку: каждый шаг снимает целый класс причин.

1. **Он вообще запущен — и на каком порту?** `systemctl status termit-hysteria` и `ss -lunp | grep ':443'`.
   Если юнит не `active`, причина в `journalctl -u termit-hysteria -n 50`: обычно нет бинарника (его
   ставит `termit-uv init`) или конфигурация перестала разбираться после правки руками.
2. **Дело в юните или в машине?** Перезапустите и посмотрите журнал. Если старт убивает ядро через секунды —
   это сработал потолок памяти (`journalctl -k | grep 'Killed process'` назовёт процесс). Так выглядит
   ограниченный GO-2026-5288: транспорт возвращается, остальные сервисы узла этого не замечают.
3. **Узел может прочитать свой ключ?** `ls -l /var/lib/termit/uv/certs`: `privkey.pem` должен быть
   `-rw-r----- root termit-hy` в каталоге `drwxr-x--- root termit-hy`. Иначе узел ставился старой
   сборкой; права исправляет `termit-uv init`, а не `chown` вручную.
4. **Межсетевой экран его пропускает?** При включённой таблице `nft list chain inet termit_uv input | grep 'udp
   dport 443'` должен показать accept, а `security.firewall.udp_ports` — содержать `443`. `termit-uv init`
   откажется включать транспорт без этого, так что узел с включённым транспортом и без правила правили
   руками.
5. **Узел знает эти учётные данные?** `grep -c '^    u' /etc/termit/uv/hysteria.yaml` — число принятых
   пользователей: устройство самого узла, локальные устройства, все пиры и проба сервера. Если имени из
   ссылки в файле нет, узел не синхронизировался после смены набора пользователей.
6. **Может, сломан клиент?** Прежде чем винить узел, проверьте, что у клиента вообще работает TLS: на той
   же машине `hysteria client -c client.yaml` с той же ссылкой, затем запрос через его SOCKS-порт. Если
   HTTPS падает с ошибкой из TLS-библиотеки клиента, а обычный HTTP через тот же туннель проходит —
   туннель в порядке, клиент нет. Это не гипотеза: `curl` на Windows, собранный с Schannel, валил все
   HTTPS-запросы через здоровый транспорт.
7. **UDP или путь?** Если рукопожатие не завершается, а обычный HTTP через тот же туннель идёт, подозревайте
   сеть: часть путей режет или душит UDP/443. `tcpdump -ni any 'udp port 443'` на узле покажет, доходят ли
   пакеты клиента вовсе; если нет — это проблема пути или межсетевого экрана, а не Termit.
8. **Клиента забанило за его же QUIC?** Если таблица включена, а accept `udp dport 443` в ней нет, QUIC-запросы
   участника попадают в scan-meter, и страж банит источник — а бан режет всё с этого адреса, включая VLESS.
   `termit-uv bans list` назовёт его как `scan`; `termit-uv bans unban <ip>` снимает бан, а
   `termit-uv firewall on` + `confirm` убирают причину. Забаненный так адрес — не сканер, а клиент, которого
   таблица не пустила.

## 13. После ребута вернулась старая таблица межсетевого экрана

`termit-uv firewall restore` — загрузочный юнит — возвращает запись, которую оставил последний подтверждённый
`on`, а запись не следует за конфигурацией. Порт, добавленный позже (`security.firewall.udp_ports: [443]`,
когда включили Hysteria2), в ядре отсутствует до следующего `firewall on`; а недостающий UDP-порт — это не
просто закрытый порт: его пакеты доходят до scan-meter.

Теперь это видно: `termit-uv firewall status` печатает применённые UDP-порты и называет разошедшиеся поля
(`udp_ports`, `ports`, `ssh_from`, `default_deny`), `termit-uv doctor` предупреждает о том же, а
`termit-uv firewall restore` пишет это в журнал загрузки. Таблицу по-прежнему применяет только `firewall on`:

    termit-uv firewall on
    termit-uv firewall confirm

Запись, которую оставит этот `on`, и восстановит следующий ребут — вместе с ней уйдёт и предупреждение.
